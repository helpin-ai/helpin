# Widget Messenger Security Integration Guide

Status: Draft customer-facing guide
Last updated: 2026-05-02

## Overview

Helpin Messenger Security verifies logged-in users in the support widget. It prevents a browser from claiming another user's email or account identity by requiring a short-lived signed token generated by your backend.

You only need this for authenticated app pages. Anonymous marketing pages can keep using the widget with just a widget key.

## Which Integration Do You Need?

```txt
Is the widget installed on a logged-in app page?
        |
        +-- no --> Use anonymous install with widgetKey only.
        |
        +-- yes --> Add Messenger Security token endpoint.
```

## Anonymous Marketing Install

Use this on public pages where visitors are not logged in.

```html
<script>
  window.helpinSettings = {
    widgetKey: "wk_live_xxx"
  };
</script>
<script async src="https://cdn.helpin.ai/sdk.js"></script>
```

Flow:

```txt
Visitor opens page
        |
        v
Widget boots anonymously
        |
        v
Visitor chats or enters pre-chat email
        |
        v
Helpin stores visitor as unverified lead
```

## Authenticated App Install

Use this inside your SaaS app after the user logs in.

High-level flow:

```txt
Logged-in user opens app
        |
        v
Frontend requests token from your backend
        |
        v
Your backend signs token with Helpin widget secret
        |
        v
Frontend boots Helpin widget with token
        |
        v
Helpin verifies token and marks user verified
```

## Step 1: Store Your Helpin Widget Secret

In Helpin, go to:

```txt
Settings -> Chat Widget -> Security
```

Copy the Messenger Security secret and store it only on your backend.

Do not put the secret in:

- frontend JavaScript
- mobile app bundles
- public repos
- build logs

## Step 2: Add A Backend Token Endpoint

Your frontend should call your backend after the user is authenticated.

Example endpoint:

```txt
GET /api/helpin/widget-token
```

The endpoint must require your normal app login session.

Security requirements for this endpoint:

- Require the user's authenticated app session.
- Apply the same CSRF protection used for other authenticated app endpoints.
- Do not allow cross-origin token reads.
- Do not cache responses in shared caches.
- Return tokens only for the currently authenticated user and account.

## Step 3: Generate A Signed Token

Required token claims:

| Claim | Description |
| --- | --- |
| `sub` | Stable user ID from your app. |
| `aud` | Helpin widget key. |
| `iat` | Issued-at timestamp. |
| `exp` | Expiration timestamp. |

Recommended token claims:

| Claim | Description |
| --- | --- |
| `email` | User email. |
| `name` | User display name. |
| `company.id` | Stable account/company ID. |
| `company.name` | Account/company display name. |
| `company.domain` | Account/company domain. |

## Node Example

```ts
import express from "express";
import jwt from "jsonwebtoken";

const app = express();

app.get("/api/helpin/widget-token", requireAuth, (req, res) => {
  const token = jwt.sign(
    {
      sub: req.user.id,
      email: req.user.email,
      name: req.user.name,
      company: {
        id: req.user.account.id,
        name: req.user.account.name,
        domain: req.user.account.domain,
      },
      aud: process.env.HELPIN_WIDGET_KEY,
    },
    process.env.HELPIN_WIDGET_SECRET,
    {
      algorithm: "HS256",
      expiresIn: "10m",
    },
  );

  res.json({ token });
});
```

## Go Example

```go
package main

import (
	"net/http"
	"os"
	"time"

	"github.com/golang-jwt/jwt/v5"
)

func helpinWidgetToken(w http.ResponseWriter, r *http.Request) {
	user := currentUser(r) // Your authenticated app user.

	claims := jwt.MapClaims{
		"sub":   user.ID,
		"email": user.Email,
		"name":  user.Name,
		"company": map[string]any{
			"id":   user.AccountID,
			"name": user.AccountName,
		},
		"aud": os.Getenv("HELPIN_WIDGET_KEY"),
		"iat": time.Now().Unix(),
		"exp": time.Now().Add(10 * time.Minute).Unix(),
	}

	token := jwt.NewWithClaims(jwt.SigningMethodHS256, claims)
	signed, err := token.SignedString([]byte(os.Getenv("HELPIN_WIDGET_SECRET")))
	if err != nil {
		http.Error(w, "failed to sign token", http.StatusInternalServerError)
		return
	}

	w.Header().Set("Content-Type", "application/json")
	w.Write([]byte(`{"token":"` + signed + `"}`))
}
```

## Step 4: Boot The Widget With The Token

```ts
async function bootHelpin() {
  const res = await fetch("/api/helpin/widget-token", {
    credentials: "include",
  });

  const { token } = await res.json();

  window.helpin("boot", {
    widgetKey: "wk_live_xxx",
    identityToken: token,
  });
}

bootHelpin();
```

## Step 5: Refresh The Token When Needed

Tokens should be short-lived, usually 5 to 15 minutes.

If your app is long-lived, request a fresh token when:

- the page reloads
- the user changes account/workspace
- the user identity changes
- Helpin reports token expiry

For long-lived SPAs, prefer a token callback:

```ts
window.helpin("configure", {
  getIdentityToken: async () => {
    const res = await fetch("/api/helpin/widget-token", {
      credentials: "include",
      headers: {
        "X-CSRF-Token": window.appCsrfToken,
      },
    });
    const { token } = await res.json();
    return token;
  },
});
```

Then boot normally:

```ts
window.helpin("boot", {
  widgetKey: "wk_live_xxx",
});
```

Passing `identityToken` directly at boot works for simple page loads. The callback is better for apps where a tab may stay open for hours.

## Step 6: Logout

When your app logs the user out, clear the Helpin widget session.

```ts
await window.helpin("shutdown");
```

Flow:

```txt
User logs out
        |
        v
App clears auth session
        |
        v
App calls helpin("shutdown")
        |
        v
Helpin clears widget session
and rotates browser identity
        |
        v
Next visitor starts anonymous
```

## Monitor Mode Vs Enforce Mode

Monitor mode:

- Helpin verifies tokens if present.
- Existing unsigned identify still works.
- Support inbox marks identity as verified or unverified.
- Best for rollout.

Enforce mode:

- Logged-in identity requires valid token.
- Browser-only email/name identify is not trusted.
- Invalid tokens are rejected.
- Best after successful monitor-mode validation.

## Common Failure Modes

| Error | Cause | Fix |
| --- | --- | --- |
| `missing_token` | No token was sent. | Fetch token before booting widget on logged-in pages. |
| `invalid_signature` | Wrong secret or changed token. | Check backend secret and signing algorithm. |
| `expired_token` | Token `exp` is in the past. | Generate a fresh token. |
| `invalid_audience` | `aud` does not match widget key. | Use the correct widget key. |
| `missing_subject` | `sub` is empty. | Include stable user ID. |
| `unsupported_alg` | Token does not use HS256. | Sign with HS256. |
| `csrf_failed` | Your token endpoint rejected the browser request. | Send the same CSRF token/header your app requires. |

## What Not To Do

Do not sign tokens in browser code.

```txt
Bad:
frontend has HELPIN_WIDGET_SECRET
frontend signs token
any visitor can inspect secret
any visitor can impersonate users
```

Do not use email as your only stable user ID if your app has real user IDs.

```txt
Better:
sub = "user_123"
email = "jane@example.com"

Weaker:
sub = "jane@example.com"
email = "jane@example.com"
```

Do not forget logout.

Shared browsers can leak prior conversation access if widget sessions are not cleared.

## Deployment Checklist

- [ ] Create Helpin Messenger Security secret.
- [ ] Store secret in backend environment.
- [ ] Add authenticated token endpoint.
- [ ] Protect token endpoint with your normal auth and CSRF controls.
- [ ] Include `sub`, `aud`, `iat`, and `exp`.
- [ ] Include email and company claims if available.
- [ ] Boot widget with `identityToken`.
- [ ] Use `getIdentityToken` callback for long-lived SPAs.
- [ ] Call `helpin("shutdown")` on logout.
- [ ] Run in monitor mode.
- [ ] Confirm verified identities in Helpin inbox.
- [ ] Enable enforcement when stable.
